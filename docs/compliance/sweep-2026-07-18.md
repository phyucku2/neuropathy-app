was re-verified by hand and holds.

## HIGH

### 1. [HIGH] EMR lab pull aborts the entire import with an HTTP 500 on realistic FHIR bundles

- **Dimension / file:** fn-ingestion-emr — `backend/app/fhir/mapping.py`
- **Evidence:** mapping.py:34-35 `_status_from_fhir` does `LabStatus(status.replace("-", "_"))`; LabStatus (schemas/lab.py:20-24) defines only preliminary/final/amended/corrected/entered_in_error. mapping.py:94-95 `_loinc_coding` raises ValueError when Observation.code has no LOINC coding. mapping.py:126 constructs `LabResultIn(...)`, whose model_validator (schemas/lab.py:88-93) raises when there is no value/value_text or a numeric value with no unit, and whose loinc_code Field pattern `^\d{1,7}-\d$` rejects non-matching codes. client.py:40-46 iterates `bundle_from_fhir` with no per-entry guard; service.py:283-288 `pull_labs` calls it with no try/except; emr.py:145-148 the route catches ONLY EmrError.
- **What & why:** The flagship EMR pull maps every Observation in the fetched Bundle through `from_fhir`/`LabResultIn`. A single entry that a real EHR search-set routinely contains makes the whole pull throw an uncaught ValueError/pydantic ValidationError: (a) FHIR Observation.status of `registered`, `cancelled`, or `unknown` — all valid R4 codes absent from the 5-value LabStatus subset; (b) a panel/grouping Observation (e.g. a CBC header) with `hasMember` but no valueQuantity/valueString; (c) a lab coded only in a local/non-LOINC system; (d) a valueQuantity with no unit and no code; (e) a missing effectiveDateTime; or (f) a search Bundle entry whose resource is an OperationOutcome (no required `code`), which fails `Bundle.model_validate` in client.py:42. Because pull_labs and the route surface nothing but EmrError, any of these becomes a bare HTTP 500 and the patient imports ZERO labs — one un-mappable row poisons every valid row in the same pull. This is a core-function defect: EHR lab bundles very commonly include grouping observations, non-LOINC local codes, and non-final statuses.
- **Recommendation:** Make bundle_from_fhir resilient: wrap each entry's from_fhir mapping in try/except, skip un-mappable entries and accumulate a per-record warning/skip count (mirroring the biomech/wearable reject-not-crash posture) rather than aborting the batch. Broaden LabStatus (or map unknown/registered/cancelled explicitly, e.g. drop or coerce) and treat missing LOINC/value/unit/effectiveDateTime as a per-entry skip. As defense in depth, have pull_labs translate any residual non-EmrError into a 502 EmrError so a malformed EHR response is never a 500.
- **Verifier:** Every claim verified against the code. The batch mapper bundle_from_fhir (mapping.py:148-150) is an unguarded list comprehension; fetch_lab_observations (client.py:41-43) wraps neither Bundle.model_validate nor bundle_from_fhir in try/except; pull_labs (service.py:283-288) has no try/except around the fetch; and the route (emr.py:145-148) catches ONLY EmrError, so any ValueError/pydantic ValidationError becomes a bare HTTP 500 and the pull imports zero labs. Each poison-entry vector is real: (a) LabStatus (lab.py:17-24) defines only 5 statuses and _status_from_fhir (mapping.py:34-35) calls LabStatus(status.replace('-','_')), so valid R4 codes registered/cancelled/unknown raise ValueError; (b) a grouping Observation with no value hits _require_a_value (lab.py:88-90); (c) a non-LOINC code hits _loinc_coding raise (mapping.py:95); (d) a valueQuantity with no unit/code hits lab.py:91-92; (e) missing effectiveDateTime raises at mapping.py:105-106; (f) an OperationOutcome entry fails Bundle.model_validate at client.py:42 because BundleEntry.resource is typed Observation (resources.py:76-77) with required status/code. No mitigating control exists: tests (test_fhir_mapping.py, test_emr_client.py, test_emr_endpoints.py) only assert unit-level raises for missing LOINC/effective-time and never exercise a heterogeneous bundle or assert graceful skip; the 502 tests cover the OAuth callback, not the pull; and the LabStatus docstring documents scope, not a crash-on-others decision. The codebase's own biomech ingestion path (biomech.py:51-53,72-125) is explicitly reject-not-crash with imported/skipped/warnings counts, confirming the EMR pull is an inconsistency, not an intentional design. High is correct: it is the flagship EMR pull and real EHR lab search-sets routinely contain non-final statuses, panel observations, local codes, and OperationOutcome entries, any one of which aborts the whole import as an opaque 500. Not critical because it fails closed (zero import, no corruption/PHI leak).

## MEDIUM

### 2. [MEDIUM] nginx error_log leaks patient UUIDs and single-use OAuth code/state on proxy errors; the config's safety justification is factually incorrect

- **✅ Status (2026-07-18):** Partially remediated. The factually-incorrect comment is corrected — `nginx.conf.template` now states the error stream carries the full request line (path + query) and labels it POTENTIALLY PHI-BEARING for retention/access-control. The deeper fix (route the error stream off the app-log pipeline, or relay the OAuth code/state off the query string) remains an ops/architecture follow-up, tracked in the remediation plan below.
- **Dimension / file:** hipaa-phi-logging — `frontend/nginx.conf.template`
- **Evidence:** nginx.conf.template:19 `error_log /dev/stderr error;` with the justifying comment at lines 15-18: "on a hard proxy error nginx appends the request line to its message ... this is the ONE place a raw path could surface ... acceptable only because at `error` level for these proxy paths the message never carries the query string, and the access log below is fully PHI-free". The proxied API locations forward the full URI including query: lines 110-136, e.g. line 114 `proxy_pass http://$backend_origin$request_uri;` and the id-bearing clinic route line 132 `location ~ ^/clinic/patients/[^/]+/.+ { proxy_pass http://$backend_origin$request_uri; }`. The authenticated /emr/callback relay puts the OAuth code+state in the query string: frontend/src/api/endpoints.ts:159-161 `const query = new URLSearchParams({ state, code }); return request(`/emr/callback?${query.toString()}`);`, and that request carries a bearer so nginx's `if ($http_authorization = "")` guard (line 111) is false and it is proxied (not rewritten to index.html).
- **What & why:** nginx's error-log messages for upstream/proxy failures include the raw request line in the `request:` field (and again in the `upstream:` field), and that request line contains the full URI INCLUDING the query string — not just the path. The config comment asserts the error message "never carries the query string" for proxy paths; that premise is wrong. Consequences on any hard proxy error (backend down, refused connection, timeout, invalid upstream response — precisely the correlated, high-volume conditions during an outage): (1) `/clinic/patients/<patient-uuid>/...` request lines write the patient UUID to captured stderr, and (2) `/emr/callback?state=...&code=...` request lines write the single-use SMART OAuth authorization code and state to captured stderr. These are exactly the identifiers the deliberately-designed `phi_free` access-log format (lines 42-45) strips to satisfy the PHI-free logging guarantee (ADR-0018 §4). The error_log path therefore silently defeats that guarantee for error conditions, and it is justified by an incorrect claim about nginx behavior, so the residual exposure is undocumented in effect.
- **Recommendation:** Do not rely on the (incorrect) assumption that error-level proxy messages omit the query string. Options: (a) keep proxy error_log but route it so it is not captured as an application log stream, or scrub it; (b) reduce the risk surface by acknowledging in the comment that BOTH the raw path (patient UUID) and query string (OAuth code+state) can appear, and treat the error_log stream as potentially-PHI-bearing for retention/access-control purposes; (c) where feasible, avoid carrying the OAuth code/state in the query string of the proxied backend call (e.g. relay them in a POST body / header) so they cannot land in any request-line log. At minimum, correct the code comment so the accepted-risk decision is based on accurate nginx behavior.
- **Verifier:** The finding's central technical premise is correct and every cited code path checks out.

nginx behavior: On a hard upstream/proxy error (connect refused, timeout, upstream prematurely closed, invalid response) nginx logs at `error` level with request context, and its error handler appends `request: "<r->request_line>"`. The request line is the raw HTTP first line, which ALWAYS includes the query string (e.g. `GET /emr/callback?state=...&code=... HTTP/1.1`), plus an `upstream:` field built from the URI-with-query. So the config's claim (frontend/nginx.conf.template:17-18, "at `error` level for these proxy paths the message never carries the query string") and the identical claim in ADR-0018 §4 (docs/decisions/2026-07-14-adr-0018-deployment-and-infrastructure.md:109, "that message carries no query string") are factually wrong.

Code paths confirmed: nginx.conf.template:19 `error_log /dev/stderr error;` writes to the captured stderr stream. Proxy locations forward `$request_uri` including query — line 114 (`/emr/callback`), line 132 (`location ~ ^/clinic/patients/[^/]+/.+`, patient-UUID-bearing). The callback is proxied (not shelled) when a bearer is present: line 111 `if ($http_authorization = "")` is false, so `proxy_pass` on line 114 runs. frontend/src/api/endpoints.ts:159-161 places the single-use SMART OAuth `code`+`state` in the query string, and frontend/src/api/client.ts:93-94 attaches `Authorization: Bearer` for that (non-anonymous) request. So during a backend outage these request lines (patient UUID; OAuth code+state) land in captured stderr, defeating the ADR-0018 §4 PHI-free-logging guarantee for error conditions.

No mitigating control catches this: backend/tests/test_nginx_logging.py only asserts the `access_log` `phi_free` format omits path/query variables (lines 22, 46-50); it does not constrain `error_log`. The ADR does acknowledge the raw-path (UUID) leak as "the one unavoidable place a raw path can surface," but explicitly rules out the query string — so the OAuth code+state exposure is genuinely undocumented/mis-justified, not an accepted residual.

Severity medium is appropriate, not higher: the leak manifests only on hard proxy errors into an access-controlled ops error stream, and the OAuth authorization code is PKCE-bound (single-use, requires the code_verifier that never leaves the backend), limiting replay value. Not lower than medium: it silently defeats a HIPAA PHI-free-logging guarantee, is high-volume/correlated precisely during outages, and the accepted-risk decision rests on a provably incorrect nginx-behavior claim, so the stream is not being treated as PHI-bearing for retention/access.

### 3. [MEDIUM] Idempotent ingestion is not atomically enforced — no unique constraint on (patient_id, import_key), only read-then-write

- **✅ Status (2026-07-18):** Remediated. Migration `0008` replaces the non-unique index with a partial UNIQUE index `uq_observation_patient_import_key … WHERE import_key IS NOT NULL`, and `ObservationRepository.add_if_absent` (savepoint-scoped conflict→skip) is now the write for every import-keyed ingest path (EMR labs, patient lab upload, biomech, wearable/CGM). Idempotency is a DB invariant; a concurrent duplicate is a graceful skip, not a double-count or a 500. Unit + cross-session Postgres integration tests added.
- **Dimension / file:** soc2-processing-integrity — `backend/alembic/versions/0001_initial.py`
- **Evidence:** Migration 0001 lines 266-269 create ix_observation_patient_import_key with unique=False; the ORM model mirrors this (models/observation.py:113, an Index not a UniqueConstraint). PostgresObservationRepository.add() is a plain session.add()+flush() with no ON CONFLICT (repositories/postgres.py:333-336). Every ingest route enforces idempotency purely by a prior existence probe then insert: labs (routes/ingestion.py:89-112), wearable (148-176), biomech (routes/biomech.py:84-101).
- **What & why:** The documented invariant across the codebase is that the same real-world datum 'is never double-counted in the analyzable dataset' (ingestion/labs.py:73-83, schemas/ingestion.py:42-46, schemas/wearable.py:105-109). That guarantee rests entirely on a check-then-act sequence (existing_import_keys probe, then add) with no database-level uniqueness and no row/advisory lock. Two concurrent requests carrying the same import_key (a mobile client retry over a flaky network, or a double-tap — both common) each run existing_import_keys in their own transaction, each see the key absent, and each insert; both commit successfully, so the identical content-identity value enters the analyzable dataset twice and is double-counted in the trajectory and NSI. This is a real processing-integrity gap for SOC2: the system does not actually enforce the completeness/accuracy control it documents. Notably the same codebase already uses SELECT FOR UPDATE / FOR SHARE to close analogous TOCTOU windows on other invariants (repositories/postgres.py:155 ops-last-active, :241 consent authority), so the protection pattern exists but was not applied to the ingestion idempotency path.
- **Recommendation:** Add a partial UNIQUE constraint on (patient_id, import_key) WHERE import_key IS NOT NULL and switch the write to an idempotent upsert (INSERT ... ON CONFLICT DO NOTHING), treating a conflict as 'skipped'. This makes idempotency a database invariant rather than an advisory read-then-write race.
- **Verifier:** Every factual claim checks out against the real code (note: the ingest routes live under app/api/routes/, not app/routes/, but the cited line numbers and content match).

1. No DB-level uniqueness. Migration 0001_initial.py:265-270 creates ix_observation_patient_import_key with unique=False; the ORM mirror in models/observation.py:113 is an Index(...) in __table_args__, not a UniqueConstraint. Grep of all 7 migrations (0001-0007) finds no unique index/constraint on import_key anywhere.

2. Write is a bare insert. PostgresObservationRepository.add() at repositories/postgres.py:333-336 is exactly self._session.add(observation) + flush(), with no ON CONFLICT / upsert (grep for on_conflict across the repo returns nothing).

3. All three ingest paths are check-then-act across transactions. Labs (api/routes/ingestion.py:89-112), wearable (148-176), biomech (api/routes/biomech.py:84-101) each call service.observations.existing_import_keys(...) then loop add(). The in-request `seen` set only dedupes within one batch; it gives no protection against a second concurrent request. No advisory lock, no SELECT FOR UPDATE, no row lock on the import path.

4. The race is genuine under the default READ COMMITTED isolation (no isolation override found in app/). Two concurrent requests with the same import_key each read the key as absent and each insert, both commit → the same content-identity row lands twice and is double-counted in trajectory/NSI, directly defeating the documented "never double-counted in the analyzable dataset" invariant (ingestion/labs.py:73-83).

5. The finding's claim that the protective pattern exists but wasn't applied here is also accurate: with_for_update() at postgres.py:155 (ops last-active TOCTOU) and with_for_update(read=True) at :241 (consent authority TOCTOU, ADR-0013) close analogous windows.

No mitigating control exists. The SOC2 gap register (docs/compliance/gap-register/soc2.md:40) lists "import idempotency" as met-in-code for PI1.1-PI1.3 and even notes "PI correctness enforced by tests not a monitored control" — it does not acknowledge or accept this concurrency/atomicity gap, and no ADR documents accepting the race. Tests cover sequential dedup only; none exercise concurrency.

Severity medium is correct: it defeats a documented processing-integrity control and can skew a clinical score, but the trigger is a narrow concurrency window, the result is duplicated (not corrupted or lost) valid data, and there is no security/authorization impact. Not high (no data loss/corruption, narrow trigger), not low (real defeat of a claimed SOC2 control with clinical-score impact).

### 4. [MEDIUM] Unbounded EMR FHIR pagination runs inside the request DB transaction, coupling pool occupancy to a third-party EMR and pinning the async task

- **✅ Status (2026-07-18):** Remediated (paging bound). `emr/client.py` now caps the `next`-link loop at `MAX_LAB_PAGES` (100) and a cumulative `LAB_PULL_DEADLINE_SECONDS` (60s), raising a graceful 502 `EmrError` so a pathological/self-referential FHIR server can no longer pin a pooled connection indefinitely. Test added (`test_pagination_is_bounded_against_a_pathological_ehr`). The broader session-per-phase refactor (decouple external EMR I/O from the open DB transaction) remains the documented follow-up in `db/session.py`.
- **Dimension / file:** soc2-availability — `backend/app/emr/client.py`
- **Evidence:** client.py:40-44 `while url:` loops over Bundle `next` links with no page cap and no cumulative deadline, each iteration `await self._transport.get_json(...)` (transport.py:24 per-request timeout=20.0s, not cumulative). Called from emr.py:146 `await service.pull_labs(connection_id)`, which runs inside the request transaction opened by db/session.py:74 `async with maker() as session, session.begin():` — service.pull_labs first does `get_connection`/`secret_store.get` (SQL, checks out a pooled connection) at emr/service.py:267-273 BEFORE `client.fetch_lab_observations` at emr/service.py:284.
- **What & why:** The lab pull follows FHIR paging in an unbounded loop with no maximum page count and no overall time budget (only a per-GET 20s timeout). Because the request's DB transaction is already open (a pooled connection is checked out before the EMR I/O begins), that connection is held for the full duration of the multi-page external fetch. A slow, large, or pathological/compromised FHIR server (e.g. one that always advertises a `next` link, or a self-referential next URL) makes a single pull take minutes or never return, pinning a worker async task and one of the pool's connections (pool_size=10 + max_overflow=20 per worker, db/session.py:44-47). db/session.py:38-39 already flags this coupling as a known limitation ("span external EMR I/O ... session-per-phase is the follow-up"). Under enough concurrent slow pulls the pool saturates; `/readyz` (health.py:68-70) also draws a connection from that same pool bounded to only 2s, so it then returns 503 and the orchestrator pulls the instance from rotation (Azure readiness periodSeconds=15/failureThreshold=3, main.bicep:380-390). Net effect for SOC2 availability: a degraded or hostile EMR dependency can degrade the app's own availability, and a single endless `next` chain can hold a connection indefinitely. The single-call error path is graceful (raise_for_status -> EmrError -> HTTP mapping), but the paging loop itself is not bounded.
- **Recommendation:** Bound the pull: add a maximum page count and/or a cumulative wall-clock deadline across the whole `fetch_lab_observations` loop (not just per-request), and stop with a graceful EmrError when exceeded. Additionally, decouple the external EMR I/O from the open DB transaction (the documented session-per-phase refactor) so a slow EMR cannot hold a pooled connection, and consider giving `/readyz` a dedicated short-lived connection or a NullPool probe so readiness cannot be starved by request/EMR pool pressure.
- **Verifier:** Every load-bearing claim is confirmed in the actual code, and no mitigating control exists.

1. Unbounded pagination: client.py:40-44 `while url:` follows Bundle `next` links (`url = _next_link(payload)`) with no page counter and no cumulative wall-clock deadline. Confirmed.
2. Per-GET-only timeout: transport.py:24 `HttpxTransport.__init__(..., timeout_s: float = 20.0)` sets `httpx.AsyncClient(timeout=timeout_s)` — a per-request timeout, not cumulative across pages. A FHIR server that returns a page (or a self-referential `next`) within 20s each time loops forever. Confirmed.
3. Runs inside the request transaction with a pooled connection already checked out before the EMR I/O: session.py:74 `async with maker() as session, session.begin():` opens the request transaction; service.py:267 `record = await self.get_connection(...)` and service.py:273 `tokens = await self.secret_store.get(...)` execute SQL (checking out a pooled connection) BEFORE service.py:284 `client.fetch_lab_observations(...)`. In DB mode deps.py:286-302 wires EmrService with PostgresEmrConnectionRepository/PostgresSecretStore bound to that same request session, so get_connection is real SQL that pins the connection through the whole multi-page external fetch until request-end commit. emr.py:146 `await service.pull_labs(connection_id)` is the caller. Confirmed.
4. Pool sizing per worker: session.py:44-47 pool_size=10, max_overflow=20, pool_timeout=5. Confirmed.
5. Readiness starvation chain: health.py:68-70 `/readyz` runs `engine.connect()` on the SAME engine/pool bounded by asyncio.timeout(2.0); under pool saturation it cannot get a slot in 2s and returns 503 (health.py:61,75). infra/azure/main.bicep:383-389 readiness probe path `/readyz`, periodSeconds=15, failureThreshold=3 → the instance is pulled from rotation after sustained failures. Confirmed.
6. No mitigating control: no page cap / cumulative deadline anywhere in app/emr (grep found only token-lifetime `_MAX_LIFETIME` in backend_auth.py, unrelated); main.py adds only ErrorReporting/Metrics/RequestLogging middleware — no request-timeout middleware. The codebase itself documents this as an UNRESOLVED limitation, not a risk-accepted decision: session.py:37-39 "request transactions that (today) span external EMR I/O ... session-per-phase is the follow-up that removes that coupling." That is a planned fix, not a control.

The pull is authenticated, ownership-checked (emr.py:144), and ingest_labs capability-gated (emr.py:139), and the single-call error path is graceful (transport raise_for_status → EmrError → HTTP mapping), so this is not an unauthenticated DoS. But a single endless/self-referential `next` chain can pin one pooled connection and an async task indefinitely, and ~30 concurrent slow pulls per worker saturate the pool and flip /readyz to 503 → rotation removal — a real SOC2 availability-resilience defect where a degraded/hostile third-party EMR degrades the app's own availability. Medium is correctly rated: higher is not warranted (requires a pathological/hostile EMR or meaningful concurrency, and is auth+capability gated), lower understates the indefinite connection-pinning and the documented, still-open pool↔EMR coupling.

### 5. [MEDIUM] Empty/unset JWT_SECRET silently yields a per-worker ephemeral signing secret, breaking sessions in the default multi-worker deployment

- **✅ Status (2026-07-18):** Remediated. `config.py` normalizes a blank `JWT_SECRET=` to unset (`_empty_env_is_unset`), and the **serving-startup guard** `_check_serving_secrets` in `app/main.py` (run in the app lifespan) **hard-fails the boot** when `DATABASE_URL` is set, `JWT_SECRET` is missing, and `WEB_CONCURRENCY > 1` — the exact multi-worker case that causes the intermittent 401 storm — and **warns** (mirroring `secret_store_key`) for a single-process DB deployment where the per-process ephemeral key is still self-consistent. The check lives on the serving path, **not** in `Settings` construction, so migration/tooling (`alembic`, which never signs a token) is unaffected.
