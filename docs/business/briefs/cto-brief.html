  • Single SPA, two targets. The Android app is the same built bundle in a Capacitor shell — no second codebase. Platform differences are isolated behind three seams: platform.ts (one isNativePlatform()), refreshTokenBackend.ts (sessionStorage vs Keystore), nativeShell.ts (status bar/splash/back/App-Links). Everything else is platform-blind.
  • Dual persistence by design. Every repository has a Postgres implementation and an in-memory twin with test-pinned parity — the app boots with no database for demos and fast tests, and the integration suite runs the same tests against live Postgres.
  • Runtime config, not build config. The frontend reads its API base from /config.js at boot (container entrypoint rewrites it per environment) — one image, any environment.

3 · Security model (the part to scrutinize)

  • AuthN — Argon2id password hashing; short-lived JWT access token (memory-only on every platform, never persisted); refresh token: web = sessionStorage (tab-scoped, ADR-0015 documents the XSS tradeoff and why httpOnly cookies were rejected — no cookie/CSRF surface at all); native = Android Keystore-backed encrypted storage, revealed only after a biometric/device-credential gate that fails closed on gate errors.
  • AuthZ — role separation (patient / clinician / ops) with per-operator ops identities (the bootstrap token self-retires); clinician reads pass a single consent predicate (_may_read_patient) so panel, detail, and capability writes can't disagree; patient-held consent (share-with-clinic) is structurally outside clinician authority.
  • Server-enforced consent — capabilities gate every write path server-side (UI state is advisory); revocation and account deletion are never blockable by any toggle or kill switch — enforced by tests, not convention.
  • Secrets — EMR OAuth tokens in a Fernet-encrypted vault keyed by SECRET_STORE_KEY, deleted on revoke and on account deletion (ordered last so a mid-transaction failure can't orphan connections); repo-level: keystore-proof .gitignore, CI secret scanner that also catches Google API keys and gradle signing passwords, third-party CI actions SHA-pinned.
  • Destruction — account deletion: password re-auth (rate-limited 5/15min with bounded PHI-free denial audits), single transaction, FK-safe order across all 7+ stores, audit history retained anonymously via ON DELETE SET NULL.
  • PHI hygiene — logs and metrics are PHI-free by construction (route templates not raw paths; whitelisted event fields); audit covers reads and writes; Android allowBackup=false; no cleartext traffic.

4 · Quality system (how changes ship)

  • Process — one portion = one PR. Implementation → two independent adversarial reviews (security/privacy + correctness, prompted to find concrete failure scenarios, verified per-finding) → fixes with regression tests → merge. Review findings are real: they've caught a permanent-lockout TOCTOU, an OAuth-code-leaking nginx log, a biometric fail-open, a WebView status-bar contrast bug, citation errors in compliance docs.
  • Gates (all blocking) — backend: ruff, mypy --strict, pytest 100% coverage including live-Postgres integration + migration up/down. Frontend: strict tsc, zero-warning ESLint, Prettier, 157 unit tests ≥90% coverage (deterministic — file-serial after a contention flake was diagnosed), production build. 31 Playwright specs drive the real built bundle in Chromium with a zero-console-error gate that is itself self-tested (proven to fail on a real error). Android: APK assemble job. Plus dependency audit, license allowlist, secret scan, Docker builds.
  • Docs as code — 26 ADRs; a lessons log of preventive rules (each added the day its mistake happened); runbooks for deploy, backup/restore, incident response, Play release, EMR registration.

7 · Scale & cost posture

  • Pilot topology — 1 small app node (gunicorn/UvicornWorker, Prometheus multiprocess-safe) + managed Postgres ≈ $55–110/mo on AWS with a $0 self-serve BAA. Nothing in the architecture assumes a single node except the documented keyless dev mode.
  • Hot paths are boring — reads are per-patient indexed queries; the trajectory engine is deterministic in-process compute; the only external I/O is EMR pulls (async) and the optional AI call (off request path). No queues/workers needed until ingestion volume demands them.
  • Observability from day one — PHI-free metrics with alert rules written, request-ID-correlated logs, error seam ready for a self-hosted collector.

CTO bottom line: a small, strictly-typed, heavily-gated codebase with security decisions written down and tested, not implied. The deliberate constraints — synthetic data only, consent enforced server-side, PHI-free telemetry, files-only migrations, one-portion-one-PR — mean the risky work ahead (real PHI, billing evidence, production EMR) lands on rails that already exist. The biggest genuine risks are external: the FDA/SaMD determination and the compliance sign-offs, both already packaged for professional review.
